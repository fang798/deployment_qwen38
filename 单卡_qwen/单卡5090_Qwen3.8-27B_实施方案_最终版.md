# 单卡 RTX 5090：Qwen3.8-27B 从 Docker 部署到商业 API 的实施方案

定稿日期：2026-10-26。**方案和配套文件已准备；目标 GPU 尚未部署、显存和速度尚未实测。** 新 agent 先读本文件即可实施；有争议的原文与证据见[核验说明](Gemini方案核验与选型依据_2026-10-26.md)。

## 1. 本次确定的路线

**一张已分配的 RTX 5090 32GB → Docker 中的官方 vLLM → New API、客户 API、计费充值、监控与压测 → 通过全链路验收 → 再做卸载和性能优化。** 官方运行失败时先查配置与版本，再查明确的上游修复；社区补丁仅用于已经定位的问题。

| 项目 | 本次决定 |
|---|---|
| 主模型 | `nvidia/Qwen3.8-27B-NVFP4`，revision `482ca0f3832238542f8f5295dde86b5f22711d80` |
| 选择理由 | 当前是 NVFP4＋FP8 混合精度；3 个权重分片合计 **21,921,697,280 bytes＝20.42 GiB**，有 NVIDIA 发布的量化说明及评测，保留单卡调试空间。[配置](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4/blob/482ca0f3832238542f8f5295dde86b5f22711d80/hf_quant_config.json)、[文件](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4/tree/482ca0f3832238542f8f5295dde86b5f22711d80) |
| 推理运行时 | 官方 **vLLM v0.32.0**，镜像及其他组件都固定 digest，见配套 `.env.example`；不用浮动 nightly 自动升级 |
| 第一份运行配置 | TP=1，纯文本，16,384 总上下文，最多 4 个活动序列，batch tokens=2,048，eager，**BF16 KV**，无 MTP、无 CPU offload |
| 商业平台 | New API＋PostgreSQL＋Redis；HTTPS 用 Caddy；Prometheus＋Grafana 起步，再补 GPU/主机指标和通知 |
| 首发产品 | `qwen-27b`，OpenAI 兼容 Chat Completions，快速档、文本和已验收 tools；总上下文 16K、最大输出 2,048、每 Key 并发先限 1，总准入按压测结果确定 |
| 回退/对照 | 官方 Recipe 实测过的 **Inferact 单卡 eager 配置**；Unsloth 留作后续量化对比，均须固定 revision 并重测 |

这里是 27B 稠密混合注意力模型，**不是 Flash-Next MoE**。不沿用四卡的 EP、PLE/Engram offload、PEDIA r10、PCIe all-reduce 参数。`--dtype bfloat16` 是运行激活等浮点张量的选择，不会把已量化权重整体展开成 BF16；量化方案由 checkpoint 自动识别。依据：[模型配置](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json)、[vLLM ModelOpt 支持](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/model_executor/layers/quantization/modelopt.py)。

Inferact 的优势是已有官方单卡实测可供排障；若只在 Inferact 与 Unsloth 中选一份去复现官方单卡案例，优先 Inferact 有道理。但不能仅凭默认示例就判定它更快或质量更高：其当前权重约 24.57 GiB，比 Unsloth 大约 2.76 GiB、比本次 NVIDIA 主选大约 4.15 GiB。NVIDIA 的当前 revision 与它**不是同一份量化**；本次主选依据是空间和量化资料，仍待本机验收，不能写成已证明优胜。

## 2. P0：准备一张卡和 Docker

目标宿主推荐 Linux x86_64、64GiB RAM、200GB 可用 SSD/NVMe；32GiB RAM 属于受约束候选，以实际加载峰值判断。CPU/KV offload 实验需要另外预留内存。宿主安装 NVIDIA 驱动、Docker Engine、Compose 插件、NVIDIA Container Toolkit，以及常见 shell 工具/openssl；**Python、模型下载器、SDK、推理与压测都放容器里。宿主无需另装 CUDA Toolkit 或 vLLM。**

先执行并归档：

```bash
nvidia-smi --query-gpu=index,uuid,name,memory.total,memory.used,driver_version --format=csv
nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_memory --format=csv
free -h
df -h
docker version
docker compose version
```

只选择已分配、空闲的一张卡，记录 UUID；多卡服务器也只暴露这张。不要终止别人的进程。主镜像元数据为 CUDA **13.0.2**；CUDA 13.x 的驱动兼容性基线是 R580 或更新，还要满足 5090 与 JIT 的实际要求。容器测试通过后再继续，不绕过驱动兼容检查。[NVIDIA 兼容表](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)

缺 Docker/Toolkit 时按[Docker 安装文档](https://docs.docker.com/engine/install/)和[NVIDIA Toolkit 安装文档](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)安装；更改共享机器的驱动或重启 Docker 前检查在用服务。Docker GPU 指定方式见[官方 Compose 文档](https://docs.docker.com/compose/how-tos/gpu-support/)。

把本目录的 [docker 配套文件](docker/compose.yaml)复制到目标服务器 `/srv/qwen27`；无权限则换成有权限的持久目录，以下路径统一替换：

```bash
cd /srv/qwen27
bash init-env.sh GPU-替换为已分配显卡的真实UUID
docker compose config --quiet
docker compose pull vllm
docker compose run --rm --no-deps --entrypoint /bin/sh vllm -c nvidia-smi
docker compose run --rm --no-deps --entrypoint python3 vllm -c \
  'import torch,vllm; print(vllm.__version__,torch.__version__,torch.version.cuda); print(torch.cuda.device_count(),torch.cuda.get_device_name(0),torch.cuda.get_device_capability(0)); print(torch.ones(1,device="cuda"))'
```

`init-env.sh` 生成随机凭据，拒绝覆盖已有配置。`.env` 和 `secrets/` 不进 Git、不贴报告；`docker compose config` 的完整输出会展开秘密，日常使用 `--quiet`。环境中的 GPU 编号重排正常，以 UUID 对照。

**通过：** 容器只见一张目标 5090，CUDA 张量运算成功，版本/驱动/空闲 RAM/磁盘已记录。资料检索成功不能代替这一步。

## 3. P1：只启动官方 vLLM，先获得真实输出

### 3.1 下载并验证

```bash
cd /srv/qwen27
docker compose build tools
docker compose run --rm --no-deps tools python download.py
docker compose run --rm --no-deps --entrypoint vllm vllm serve --help=all > reports/vllm-help.txt
docker compose up -d vllm
docker compose logs -f --tail=150 vllm
```

下载脚本使用固定 revision，检查索引与 3 个分片的大小、公布的 SHA256，输出 `reports/weights.json`。镜像、工具依赖和权重清单已经固定；执行时记录实际 image ID、vLLM/Torch/FlashInfer/Transformers 版本。首次 JIT 和下载耗时随网络/CPU/缓存变化，不承诺 3 分钟启动。

配套 `compose.yaml` 已给出完整启动参数。首轮保留 `--language-model-only`、`--enforce-eager` 和 BF16 KV，便于建立基准；这是低复杂度起点。权重中没有校准 KV scale，BF16 KV 可先绕开 FP8 KV 的额外缩放变量。理论上全注意力部分 BF16 KV 为 64KiB/token、FP8 为 32KiB/token，**另有 GDN 状态、分块对齐、workspace 和并发开销**，不据此承诺 131K/262K 请求一定放得下。

### 3.2 功能测试及进入下一阶段的条件

```bash
docker compose run --rm --no-deps tools python smoke.py --repeat 30 > reports/backend-smoke.json
```

配套 SDK 脚本测试真实算术、流式最终 usage、错 Key 拒绝、工具调用及回填；它是起步验收脚本。agent 继续建立下表完整用例，保存到 `tests/`，不要用模拟响应替代模型测试：

| 项目 | P1 通过标准 |
|---|---|
| 就绪 | `/health`、认证 `/v1/models` 正常；实际推理完成，记录所选量化及 kernel 日志 |
| 功能质量 | 至少 20 个固定中文/英文/代码/JSON/抽取用例，预先写明断言；关键格式和工具用例全通过，其余业务评分达到预先规定标准 |
| 流式 | 非流式与 SSE 都有有效正文、结束原因、最终 usage；不是只收到 role/空 chunk；工具流的 JSON 能拼接解析 |
| thinking | 默认快速档正常；内部另测显式 `enable_thinking=true, reasoning_effort=medium`，区分 reasoning 与正文，检测正文被 token 预算挤空 |
| 工具 | 至少 3 个不同确定性工具用例完成模型→参数→合成工具结果→模型下一轮；基础 tools 测试不等于任意 Agent 客户端兼容 |
| 边界/稳定 | 错 Key、无效模型、超长请求明确失败且服务仍健康；连续 30 次正常调用无 OOM/挂起 |

**满足 P1 即去 P2，不先追 tok/s。** 后端 Key 保存在 `secrets/vllm_api_key`；vLLM 仅发布宿主 `127.0.0.1:8001`。API Key 不是所有运维端点的网络隔离措施，后端整个端口都保持私有。

### 3.3 启动失败怎么处理

先保存错误阶段、完整 traceback、固定版本、显存/RAM 峰值，一次改一个主要变量：

| 失败位置 | 顺序 |
|---|---|
| 镜像/CLI/模型类型 | 查真实镜像 digest、`--help=all`、本地 config 和完整分片；`qwen3_5` 是该模型合法实现名，不擅自改成 qwen3_8 |
| 权重或主机 OOM | 区分 GPU/主机内存，检查其他进程、下载完整性、加载/repack 峰值；缩上下文不能解决权重本身放不下 |
| KV/workspace OOM | 先将 seq 4→1、batch tokens 2048→1024、context 16K→8K；保持 eager；再考虑 FP8 KV 实验，不无限抬利用率 |
| kernel/量化报错 | 检查 SM120 与 ModelOpt mixed 的实际后端；让官方自动选择，别强制整模型都走单一 NVFP4 kernel |
| 生成挂起/输出异常 | 检查 thinking、模板、parser、prefix cache；用关缓存、无 tools 的最小用例复现，不能只看 health 200 |

仍失败，先查该版本上游 issue/修复，必要时换**另一份固定 digest 的官方版本**。然后才尝试 Inferact：revision `6128240ebaf4eaa7bad2b3d1c72c37d677c5f462`，独立下载/校验目录，TP1、32K 或更短、FP8 KV、eager、纯文本，参考[官方单卡实测](https://recipes.vllm.ai/Qwen/Qwen3.8-27B)。这是对照候选，仍要重跑 P1。不要使用本 kit 的 NVIDIA manifest 去校验另一模型，也不要把旧补丁整文件覆盖新 vLLM。

## 4. P2：New API、客户 Key、HTTPS 与 SDK

拓扑：`客户 → Caddy HTTPS → New API → vllm:8000`；PostgreSQL 保存账本，Redis 服务平台运行。只对公网开放最终入口，数据库/Redis、推理、Grafana 保持私有。

```bash
docker compose up -d postgres redis new-api
docker compose ps
```

在浏览器通过 SSH 隧道访问宿主 `127.0.0.1:3000`，按初始化页面创建管理员；**没有“默认 root/123456”这一步**。New API 已固定 `v1.0.0-rc.47` 的 digest，这是 RC 发布，完成本项目账务和恢复测试后才用于收费。[该版初始化源码](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.47/controller/setup.go)

配置渠道：OpenAI 类型；Base URL `http://vllm:8000`；上游模型 `qwen38-27b`；Key 使用真正的后端 Key。客户 alias 为 `qwen-27b`，模型映射 `{"qwen-27b":"qwen38-27b"}`；客户 Key 另行生成，限模型、限余额、限速。容器内的 localhost 指向它自己，不指向宿主或 vLLM。

先用[渠道参数覆盖](https://docs.newapi.pro/zh/docs/guide/console/channel-management)强制 `n=1` 和 `chat_template_kwargs={"enable_thinking":false}`，处理/删除冲突的根级 `reasoning_effort`；给 `max_tokens` 配默认与 2,048 上限，处理 `max_completion_tokens` 别名及两字段冲突。16K 是模板＋tools＋输入＋输出的总和。禁止静默截断用户输入来伪装支持；不开放客户端自带 chat template、无界采样/输出或其他运维参数。**实际发绕过请求确认规则生效**；平台未覆盖的准入/字段校验补最小适配，不把前端提示当强制限制。

把测试客户 Key 用安全编辑器写入 `secrets/customer_api_key`，权限 600，再测真正的客户路径：

```bash
docker compose run --rm --no-deps \
  -e TEST_BASE_URL=http://new-api:3000/v1 -e TEST_MODEL=qwen-27b \
  -e TEST_API_KEY_FILE=/work/secrets/customer_api_key \
  tools python smoke.py > reports/gateway-smoke.json
```

准备域名 A/AAAA 记录、80/443 入站和支付回调域名后，在 `.env` 填 `PUBLIC_DOMAIN`、`ACME_EMAIL`，再启动：

```bash
docker compose --profile edge up -d caddy
```

Caddy 配置保留 SSE 流式行为和客户端断开取消；不额外加响应缓冲或生成请求自动重试。New API 也须验证取消传递、空闲超时及出流后的重试策略。补充 HTTPS 会话 Cookie、管理访问限制、可信代理/来源配置。依据：[Caddy 流式代理说明](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#streaming)。

客户 SDK 用 `base_url=https://你的域名/v1`、客户 Key、`model=qwen-27b`；基础调用参数 `messages`、`max_tokens=128`、`stream=True/False`。先验证标准 SDK/简单客户端，再用一个实际目标 Agent 跑多轮 tools；需要 Responses 或 Anthropic 协议的客户端另行验收，不宣称 Chat Completions 通了就全部兼容。

**通过：** 新测试账号可用自己的 Key 完成流式/非流式、tools；无 Key、错 Key、越权模型被拒；参数不能绕过；域名证书有效。没有域名时可先标“本地客户 API 通过、HTTPS 待接入”。渠道测试按钮成功不足以通过 P2。

## 5. P3：把计费、充值、取消和退款做对

先发测试额度，完成“注册→余额→Key→实际调用→日志→余额变化”；再接支付沙箱，最后生产支付。**New API 是唯一客户账本**；选择 PostgreSQL 是为了延续四卡平台和恢复流程，MySQL 也能用，不存在本场景的必然性能优势。

1. 固定计价版本和币种。初期按输入/输出分别定价，缓存统一输入价；别复制 Gemini 的 OpenRouter 价格或直接把单价当 New API 倍率。核对实际 quota 换算、汇率和舍入。
2. 对照真实服务 usage 手算。例如测试费率输入 1 元/百万、输出 4 元/百万：`费用=(I+4×O)/1e6 元`。reasoning 若已计入 completion，不能再加一次；MTP 的被拒 draft 不能当客户输出收费。
3. 固定价格、模型 alias、usage 来源和 request_id，串联请求、订单、余额、消费与退款。内部压测账号单独标记；不默认记录真实客户正文和 Key。

| 必测场景 | 满意标准 |
|---|---|
| 正常、SSE、tools；以后增加的 thinking | usage、价格版本、账单、余额差额可对上；流末尾 usage 被保留 |
| 余额不足、同账户并发争抢 | 无未授权透支、重复扣费、永久预留；不能靠每 Key 并发 1 代替原子账务 |
| 客户断开、超时、后端退出、缺最终 usage | 取消及时；可信 usage 按公布规则结算，首发免收不确定部分并释放对应预留，记录异常；不永久按 max_tokens 扣款 |
| 支付回调 | 服务端验签并核对订单/金额/币种/商户；重复/乱序回调只到账一次，伪造回调不入账；不信任前端跳转 |
| Key 撤销、退款、对账 | 新请求立即拒绝；退款关联原支付与未消费可退部分；订单/支付、余额/账单、请求/usage 每日无未解释差异 |

上表是验收要求，**不是 New API 默认已全部实现的声明**。先读所选版本实现并做异常测试，缺能力时修复和回归。无生产支付凭据时可以完成沙箱，交付状态写“生产支付待接入”，不能叫正式可售。

## 6. P4：监控、压测和“满意”的尺度

### 6.1 先有监控和探测

```bash
docker compose --profile monitor up -d prometheus grafana
```

Grafana 在宿主回环 `3001`，Prometheus 在 `9090`，通过 SSH 隧道访问。配套文件已配置 vLLM 抓取、Prometheus 数据源和一条掉线规则；**还需 agent 补面板、GPU/主机采集、网关/账务统计和真实通知渠道**。这些完成前不能标“监控验收通过”。

至少采集：真实生成探测、请求成功率/429/5xx、活动与排队数、TTFT、TPOT/ITL、tokens、GPU 显存/温度/功耗、RAM/磁盘、容器重启、usage/结算/备份异常。5090 的 GPU exporter 字段需实机核实，不假定 DCGM 全支持。每分钟做一个有时限的合成真实生成探测；`/health=200` 不能发现所有卡死。实际触发一次告警及恢复，确认通知到达。

### 6.2 分清测速口径

- **TTFT**：从客户端发请求到第一个有效生成 token；另记首个可见正文时间。HTTP 头、role chunk、心跳不是首字。thinking 可能先出 reasoning，正文更晚。
- **单请求 decode tok/s**：一般用 `(输出 token−1)/(末 token 时间−首 token 时间)`；不足 2 token 时不算。同时报告 TPOT 与 ITL 停顿；有 MTP 时一个 SSE chunk 可以含多个 token，chunk 间隔不能直接当逐 token ITL。
- **总吞吐**：所有成功请求输出 token/完整墙钟时间；**goodput** 只统计满足服务目标的请求。单流速度、聚合吞吐、含 prefill 的端到端速度分别报告。

同一 tokenizer、输入/输出长度分布、thinking、采样、缓存冷/热状态和到达负载下比较。做性能实验前热身编译，单独记录进程冷启动；前缀缓存实验用多块共享长前缀并检查真实命中，不写死 784 token。

### 6.3 起步压测及通过门槛

```bash

bash bench.sh backend 4 200
bash bench.sh gateway 1 200
bash bench.sh https 1 200
```

先核对固定镜像 `vllm bench serve --help`。脚本是随机短输入、输出上限 256 的**闭环摸底**，结果在 `reports/`；要保存实际输出长度，检查重复运行的缓存状态。它不能代替下表的真实业务用例、独立固定到达率测试和账务验收。

| 负载/测试 | 起始验收要求；均为项目目标，非实测承诺 |
|---|---|
| 约 1K 输入、约 256 输出；并发 1/2/4，必要时试 8（排队） | 每档至少 200 个请求，明确实际长度分布；在声明准入下成功率≥99%，p95 可见正文 TTFT≤2s、p95 请求平均 TPOT≤80ms；报告总吞吐与停顿 |
| 代码/tools、约 8K 输入＋最多 1K 输出 | 功能正确、无 OOM，分别报告延迟；不能用较短实际输出伪装更高 tok/s |
| 长输入：约 12K 输入＋最多 1K 输出，含模板仍低于 16K | 检索/抽取用例正确、完成、无 OOM；单独报 TTFT，并测试对短请求的干扰 |
| 固定到达率至少 30 分钟、突发与过载 | 队列不持续增长；准入有界、超限明确 429；记录计划发送、实际发送、接受、完成、拒绝及发送端排队，不把闭环发送变慢当容量充足 |
| 稳定与恢复 | 受控混合负载 24h 无崩溃/持续泄漏/无法解释账务差额；3 次容器停启，至少一次等价冷启动；独立库真实备份恢复通过 |

P1 不设最低 tok/s；P4 用上述延迟/正确性找到**实际可售负载**，初期准入设为测得稳定容量的 70%–80% 后复测客户入口，不能把 `max-num-seqs=4` 当 4 个长请求可售并发。若性能阻塞 P4，保留已完成商业功能，提前做 P6 的必要优化后返回复验；不要偷偷降低标准。

备份至少包括 PostgreSQL、平台设置、价格和必要密钥（加密保存）。可用数据库容器执行：

```bash
umask 077
docker compose exec -T postgres pg_dump -U newapi -d newapi -Fc > backups/newapi.dump
```

恢复到独立数据库，核对用户/Key/余额/订单/日志；不向在线库覆盖恢复。演练推理退出、网关重启、数据库不可用及恢复，记录未结算请求的处理。单卡只有一个推理副本，重启期间不可服务。

## 7. P5：何时算全链路完成

模型基座及本次 NVIDIA 版本是 **Apache-2.0**，可按该许可商用并履行通知/分发等条件；**不套用 Flash-Next 的 MaaS 单独许可前提**。[Qwen 许可原文](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/LICENSE)。New API 所选版本是 AGPL-3.0，按实际使用/修改履行对应义务，保留该版要求的署名；商业上线还要落实经营地区、支付、隐私和客户条款。

计入 GPU/整机租金或折旧、**墙上整机功耗**、带宽、支付费率、运维、退款和闲置率，再按实测利用率定价；不按社区峰值推利润。完成一笔真实小额充值→到账→客户创建 Key→HTTPS SDK 调用→准确扣费→退款/查账，并观察受控小流量。

**最终满意：** P0–P4 全部通过，客户能独立完成上述闭环；可售负载及限制有证据，异常不乱扣费，告警/备份恢复可用，价格和客户文档齐全。缺域名或支付时明确停在本地/沙箱完成。交付 `reports/验收总表.md`，含最终版本/卡 UUID/配置、报告路径、容量与限流、费率、恢复方法、外部缺项；不含明文凭据。

## 8. P6：全链路以后，逐项学习优化与 offload

先保存已验收 profile 和回滚镜像。只有一张卡时，在维护窗口切换配置，不能同时加载两个 27B 实例抢显存。每次只改主要变量，同一负载交错跑至少 3 轮，测质量、延迟、goodput、峰值显存/RAM及功耗；所有采用的改动回归 P1–P4。

### 8.1 先改善 GPU 内正常运行

| 顺序 | 实验 | 怎么判断值得保留 |
|---|---|---|
| E1 CUDA Graph | 去掉 `--enforce-eager`；需要时以该版支持的 capture-size 配置限制到实际序列/验证 token 尺寸 | 编译/捕获成功且长短混合持续稳定；TTFT/TPOT 改善、仍留显存余量；不是只比启动是否成功 |
| E2 内置 MTP | 在胜出配置加 `--speculative-config '{"method":"mtp","num_speculative_tokens":1}'`，再对比 2/3 | 验证实际 draft/accepted 计数与正文质量，分别测并发 1/2/4；没有“3 永远最好”，接受率也不是唯一目标 |
| E3 FP8 KV | `--kv-cache-dtype fp8`，检查实际 scale 来源、是否需且支持 `--calculate-kv-scales`；与 BF16 KV 对照 | NVIDIA 此 revision 没有校准 KV scale；检查日志/实际缩放而非默认为已校准。验证长文抽取、代码、tools、缓存冷热、MTP组合，不能保证字节一致 |
| E4 调度/长度 | batch tokens 2048→4096→8192；seq 4→8；context 16K→32K，逐项比较；必要时单独试 async | 避免长 prefill 拖慢正在 decode 的请求。context 增长须有业务需求并重测；更大 batch 并非 TTFT/ITL 同时改善 |
| E5 前缀复用 | 保持稳定 system/tools 前缀；对比冷/热、多轮缓存 | 实际命中且结果正确、正文 TTFT 改善。保留默认 SHA256；哈希不是首要瓶颈，xxhash 不作为商业首发默认 |
| E6 内核/量化/外部 drafter | 最后才比较 auto 与适用 SM120 kernel、Unsloth/Inferact，或 DFlash2/DSpark | 独立固定模型、镜像与草稿 revision。先验证容量与缓存/多轮正确性，再看性能；不能把 H200/双卡结果当单卡保证 |

官方 v0.32.0 已含 DFlash2 实现和一个混合状态前缀命中修复，无需为了“有 DFlash2”先装社区分支；具体组合仍需实测。依据：[DFlash2 PR](https://github.com/vllm-project/vllm/pull/52816)、[状态索引修复](https://github.com/vllm-project/vllm/pull/55601)。

### 8.2 再做不同目的的卸载实验

| 方法 | 本项目怎么做 | 作用与满意标准 |
|---|---|---|
| 不加载视觉塔 | 首轮已用 `--language-model-only` | 这是**裁掉未售卖模态**，不是把视觉计算转 CPU；节省实际显存即可，不承诺 KV＋50%；此时不接图片/视频 |
| 权重 CPU/UVA offload | 保持同模型同长度，在独立 profile 加 `--offload-backend uva --cpu-offload-gb 1`，再试 2/4 | 观察实际 offloaded bytes、GPU/RAM峰值与 TPOT；每次 forward 经 PCIe 访问相应权重，通常损失速度。无容量需求且速度下降就回退；参数值不等于精确释放同等 GPU 空间 |
| 预取式权重 offload，后续候选 | v0.32.0 有 `--offload-backend prefetch --offload-group-size 8 --offload-num-in-group 1 --offload-prefetch-step 1`；先核实该模型/量化实际支持 | 与 UVA 在相同实际卸载量下比较，记录预取额外显存和收益；不与 UVA 参数混用，不承诺量化层一定能无损装配 |
| CPU 二级 KV/prefix cache | 主机内存足够时，先关 MTP/外部草稿，独立加 `--kv-offloading-backend native --kv-offloading-size 8`，再视内存试 16 | 留存可复用前缀块，降低缓存被 GPU 驱逐后的重算。必须观察**CPU→GPU 真正读取命中**、TTFT收益与冷/热结果一致；仅写入 CPU 不算成功 |

权重 offload 的参数单位是 GiB/卡；native KV 的 size 也是 GiB，本次单卡无需跨 rank 分摊。官方实现参考：[权重 offload](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/offload.py)、[KV 参数及 native connector 选择](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/vllm.py)。

KV offload 实验：①足够长的前缀 A 冷请求并保存结果；②用其他前缀填充到 A 的 GPU 缓存被驱逐，等待异步写入；③请求 A＋新问题，观察 CPU tier 命中、实际加载计数和正文 TTFT；④同问题冷重算作正确性对照；⑤再逐项加 MTP、取消和并发，核实混合 GDN 状态也正确恢复。无法命中先查版本、block/checkpoint 和缓存键，不能只因存在 CLI 就认为有效。

**CPU KV offload 是可复用前缀的第二层缓存，不是把 32GB 显卡自动变成可承载任意 1M 活跃上下文的显卡。** 本阶段不承诺 1M 窗口；先把 16K/32K 做可靠。以后若确需 131K/262K 或 YaRN 延伸，重新核算活跃 GPU 缓存、GDN 状态和质量，再独立立项验收。

## 9. 日常 Docker 操作与本次交付范围

| 目的 | 命令/说明 |
|---|---|
| 看状态与日志 | `docker compose ps`；`docker compose logs -f --tail=100 vllm` |
| 改参数并重建容器 | 备份配置后 `docker compose up -d vllm`；只 `restart` 不会应用新的 command/env |

| 回滚 | 恢复上一份 Compose/digest，先检查数据库迁移兼容性；不靠重新拉 latest 回滚 |
