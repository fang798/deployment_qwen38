# 单卡 Gemini 方案核验与选型依据

核验日期：2026-10-26。执行入口是[最终实施方案](单卡5090_Qwen3.8-27B_实施方案_最终版.md)，本文件用于解释选型和原方案问题。原 Gemini 文档保留原样。

核验使用模型仓库固定 revision 的 config、量化配置、许可、文件大小与 LFS SHA256；读取 NVIDIA 3 个 safetensors 的远程文件头；查询 Docker Registry manifest/config；检查 vLLM v0.32.0 源码与上游 PR。**没有目标 5090 推理结果，没有以文件大小推算出“实测显存”。** 原始记录在[核验 JSON](核验资料/单卡模型镜像与源码核验_2026-10-26.json)。

## 1. 选哪个权重

以下是当前 revision **全部 safetensors 文件合计**，包含仓库所附 MTP 文件；GiB＝bytes/2³⁰。下载体积不是运行显存，runtime 会有 repack、workspace、激活、缓存和 graph 开销。

| 仓库 | 固定 revision | 文件 bytes / GiB | 判断 |
|---|---|---|---|
| `Qwen/Qwen3.8-27B` | `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0` | 55,563,006,776 / 51.75 | BF16，不能全驻留单卡 32GB；不作为首轮 |
| `Qwen/Qwen3.8-27B-FP8` | `017b9c7af6b5689d5dd426a76e0bc077eb5ca20a` | 30,866,866,928 / 28.75 | 显存余量受限；以后可用于 CPU offload/精度对照 |
| **`nvidia/Qwen3.8-27B-NVFP4`** | **`482ca0f3832238542f8f5295dde86b5f22711d80`** | **21,921,697,280 / 20.42** | **本次主选**；有发布方说明和质量评测，混合 ModelOpt，显存空间更宽裕 |
| `unsloth/Qwen3.8-27B-NVFP4` | `f0b7c9e722f5565102fff8481c99e4d86ae099c7` | 23,417,592,488 / 21.81 | 后续对照；compressed-tensors，独立 MTP 文件，模板有差异 |
| `Inferact/Qwen3.8-27B-NVFP4` | `6128240ebaf4eaa7bad2b3d1c72c37d677c5f462` | 26,381,249,312 / 24.57 | 官方 Recipe 有单 5090 eager 实测；作为排障对照/回退 |
| `RedHatAI/Qwen3.8-27B-NVFP4` | `2889ddeeda282f17fc9e159a42125e535159a5e5` | 24,688,495,864 / 22.99 | 独立候选，不能称为 Unsloth 同源镜像 |

复核入口：[Qwen](https://huggingface.co/Qwen/Qwen3.8-27B/tree/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0)、[官方 FP8](https://huggingface.co/Qwen/Qwen3.8-27B-FP8/tree/017b9c7af6b5689d5dd426a76e0bc077eb5ca20a)、[NVIDIA](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4/tree/482ca0f3832238542f8f5295dde86b5f22711d80)、[Unsloth](https://huggingface.co/unsloth/Qwen3.8-27B-NVFP4/tree/f0b7c9e722f5565102fff8481c99e4d86ae099c7)、[Inferact](https://huggingface.co/Inferact/Qwen3.8-27B-NVFP4/tree/6128240ebaf4eaa7bad2b3d1c72c37d677c5f462)、[RedHat](https://huggingface.co/RedHatAI/Qwen3.8-27B-NVFP4/tree/2889ddeeda282f17fc9e159a42125e535159a5e5)。精确大小及 SHA256 取各仓库 API `?blobs=true`，记录已落盘。

NVIDIA 的 `quant_algo=MIXED_PRECISION`，193 个 NVFP4 层条目、208 个 FP8 层条目；MLP＋lm_head 使用 NVFP4，注意力相关投影用 FP8，其他部分仍有 BF16。配置写 `quant_method=modelopt`，运行时会选择适合 mixed 的实现，不应强制成 uniform modelopt_fp4。远程文件头还确认约 0.86GiB 视觉张量、0.79GiB MTP 张量；这些只是张量字节，不是禁用视觉后全部显存收益。它的 `kv_cache_quant_algo=null`，3 个分片头未找到 k_scale/v_scale，故首轮用 BF16 KV。[固定量化配置](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4/blob/482ca0f3832238542f8f5295dde86b5f22711d80/hf_quant_config.json)

NVIDIA 发布方评测可作为量化依据，但测试硬件是 GB300，并非本项目 5090；不能据此承诺 SM120 性能。NVIDIA 更小这一事实不等于已经证明它速度/质量全面优于其他候选。

**关于“官方 Recipe 默认 Inferact 是否更适合”：** 若只在 Inferact 与 Unsloth 中选一份复现官方单卡案例，优先 Inferact 有道理：它有明确单卡实测，证据比未经验证的显存估算直接。但官方还验证了 Unsloth 双卡运行；默认模型不等于性能/质量总排名。Recipe 的 5090 验证基于 `0.26.1rc1.dev608+g99a10304d`，不能当作本次 v0.32.0 的验收结果。本项目还要试 graph、MTP 和并发，当前 NVIDIA 留下更多空间、且有可核验的量化发布信息，因此主选 NVIDIA，Inferact 作回退。以后亲自比较时，用同一 vLLM、数据集、采样和缓存状态，分开报告容量、质量及速度；不把某次 MTP 接受率当成质量排名。

## 2. 对 Gemini 原方案逐项判断

| 原说法/做法 | 核验结论及采用方式 |
|---|---|
| 27B Dense、多模态、64 层，48 GDN＋16 全注意力 | 基本正确。实现名是 `Qwen3_5ForConditionalGeneration`；不是因为叫 Qwen3.8 就要改 config。先卖文本，保留以后视觉实验 |
| Apache-2.0、可商用 | 本次核对了实际许可文件，成立；“100% 免费商用”不能代替通知/分发义务及具体业务上线条件。与 Flash-Next 单独许可问题分开 |
| NVIDIA＝Inferact、Unsloth＝RedHat 同源镜像 | 错。量化格式、文件体积、MTP/模板均有差异；镜像/复制关系不能靠名字推断 |
| NVIDIA/Inferact 都是 24.6GiB uniform W4A4 | NVIDIA 当前为 20.42GiB mixed；Inferact 的当前量化不同。旧版本比较不能移植到今天 |
| 78.8%、89.7% 是单卡固定 MTP 接受率 | 错位使用。Recipe 中这些数字来自**双 5090、旧 vLLM、特定短请求**；单 Inferact 那次 MTP 测量另有数值。硬件/版本/数据变化都会影响 |
| 先开 131K、32 seq、8192 batch、MTP3、graphs | 激进参数叠加，不能用于定位首启问题。改为 16K、4 seq、2048、eager，无 MTP，后面逐项比较 |
| eager 或 language-model-only 都能 100% 修复 Inferact graph OOM | 不成立。Recipe 将那次 graph OOM 的修复归于 eager；视觉裁剪扩大 KV 余量，不是同一个结论；更无通用 100% 保证 |
| `--language-model-only` 是视觉 offload，KV 必增 50% | 它不加载视觉塔，不是转到 CPU 执行。特定实例的 KV 相对增幅不能视为所有权重/版本固定收益 |
| 每 token 35–37KB，因此可容纳 19万–30万 token | 只考虑部分缓存不够。全注意力 FP8 部分理论 32KiB/token；GDN 状态、对齐和工作空间要实测；池总 token 数不等于每个请求可用长度 |
| FP8 KV 必然字节一致且提速 34% | 不成立。引用测试是另一个模型/双卡环境，且有限样例一致不能证明普遍无损。FP8 KV 是独立实验，检查 scale 和业务质量 |
| `--cpu-offload-gb 6` 每生成一个 token 必精确读取 6GB | 是容量预算；实际被选权重、repack 和每次 forward/batch 访存决定代价，不是精确每 token 流量公式。允许实验，但不作为首轮提速方法 |
| native KV offload 命令存在，所以几十个会话会自动变快 | 命令有效，但需要真正 CPU 读命中和混合状态恢复；不是 HTTP 会话持久化，也不能自动放大单请求 GPU 活跃窗口 |
| 只要最新 nightly，旧“只写不读”缓存问题就解决 | 不能这样推断。必须核实修复是否进入具体 commit，并实际验收命中与正确性 |
| 784 token 是恒定的缓存零命中分界 | 错。这个值来自特定 KV/state/投机设置下的页对齐；当前源码有更细匹配/状态 checkpoint 参数。按实际日志和命中测试判断 |
| MTP=3 永远是甜点，DFlash/DSpark 单流必达 221–304 tok/s | 不成立。内置/外置草稿都有额外计算和内存；收益随负载变化。DFlash2 发布方主要评测是 H200，不是单 5090 |
| vLLM 会固定自动选择 CutlassNvFp4 | 该 kernel 确实存在且支持相应硬件；当前官方有多个候选/过滤与回退。看实际日志，不把旧 recipe 的 kernel 名当当前唯一结果 |
| xxhash 是商业默认必选 | 不采用。默认 SHA256 保留；先处理排队、prefill、thinking 和网络瓶颈，再判断哈希成本 |
| `preserve_thinking=true` 自动保证工具轨迹复用与速度提升 | 它控制模板保留已有历史 reasoning；客户端/网关必须真的回传，且额外历史增加上下文。不是保存服务端会话或必然提速开关 |
| New API 初始 root/123456、上游 Key 随便填 | 当前初始化源码不支持这套操作。初始化创建管理员，后端启用认证，渠道填真实后端 Key |
| `CalciumIon/new-api:latest` | 仓库名应小写 `calciumion/new-api`，并固定 digest；原写法还缺 TLS、稳定版本、备份及账务异常验收 |
| Docker 桥接是零延迟、一次扣费就“100% 商业闭环” | 错。网络/网关有开销；扣费一次没覆盖断流、并发、支付幂等、退款和恢复 |
| 市场价、54ms TTFT、90–300+ tok/s 可直接售卖 | 不采用为价格或 SLA。条件没有统一，必须测客户入口及可持续负载 |
| GuideLLM 一条 latest 命令即可完整压测 | 可作为另一个工具候选，但本次不依赖未锁版本的 CLI；改用与后端同版本的 `vllm bench serve`，仍需开放到达率、长文、功能和账务测试 |

结构与参数来源：[Qwen 固定 config](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json)、[官方 Recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-27B)、[固定 cache 配置](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/cache.py)、[New API 初始化](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.47/controller/setup.go)。表中否定的是通用化结论；不否认原作者在原测试条件下测得的具体结果。

官方仓库本身也要跟版本核验：DFlash2 的 PR #52816 在 2026-08-21 合并；混合缓存状态索引 PR #55601 在 2026-10-07 合并，**两者均已在 v0.32.0 的提交历史中找到**。模型卡仍给安装 PR 分支命令，不代表今天必须用它。相反，Qwen KV scale 重映射 PR #54624 本次检查仍 open；不能说“nightly 已解决一切”。NVIDIA 本次 revision 没有该类校准 scale，首轮 BF16 KV，后面单独测 FP8 的缩放方案。

依据：[52816](https://github.com/vllm-project/vllm/pull/52816)、[55601](https://github.com/vllm-project/vllm/pull/55601)、[54624](https://github.com/vllm-project/vllm/pull/54624)、[相关 DFlash 缓存错误报告](https://github.com/vllm-project/vllm/issues/60174)。旧版本的错误不自动意味着 v0.32.0 仍有同一错误；包含一个修复也不证明所有组合已通过本项目测试。

## 4. Docker 固定版本和核验边界

主镜像 `vllm/vllm-openai:v0.32.0` manifest 返回 200，固定 index digest：

`sha256:befccf0e7e4089aa23926bb6f887a85c0d46c2a99e6de5c5ffdf5cb7957c5b34`

AMD64 config 的 build commit：`5df63a7203cdb9328d824a27b682e77c7b9928be`，CUDA 13.0.2，创建时间 2026-10-18，入口为 `vllm serve`。其 AMD64 压缩 layers 合计约 9.21GB。本次只查其 registry 元数据与对应源码，没有拉完整推理镜像和运行 GPU。[发布说明](https://github.com/vllm-project/vllm/releases/tag/v0.32.0)

New API 固定 `v1.0.0-rc.47`，index digest：

`sha256:938fa2713d4946723c9e9ce3076351c33f7770699fec92d23f3a26fd95791026`

镜像 metadata commit 为 `e835b1bfc43b565d625537830dbfb19328925134`，许可标记 AGPL-3.0。[该版发布说明](https://github.com/QuantumNous/new-api/releases/tag/v1.0.0-rc.47)。数据库选择沿用官方支持的 PostgreSQL 方向，[官方 Compose](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.47/docker-compose.yml)仅作来源，密码、端口、版本及持久化已调整。

其他容器 digest 均已请求 registry 验证；完整 pin 在[环境模板](docker/.env.example)和核验 JSON。固定 digest 保证引用身份，不代表已经下载所有 layer、没有安全问题或在目标硬件上验收。生产升级仍须走功能/账务/恢复回归。

本次本地检查结果见[配套文件检查记录](核验资料/配套文件检查记录.md)。没有 5090、没有用户域名/支付配置的检查不能替代 P0–P5；正式速度、容量和可售状态由实施 agent 填写。
